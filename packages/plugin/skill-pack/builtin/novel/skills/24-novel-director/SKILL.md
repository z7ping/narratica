# 小说导演（novel-director）

## 定位

这是本项目的**默认作者入口**。

作者不需要记住 00~23 的命令。自然语言请求优先进入本 Skill，再由本 Skill 判断：
1. 当前小说处于什么阶段；
2. 现在缺什么；
3. 是否存在需要作者决定的事项；
4. 应调用哪个下游 Skill；
5. 完成后下一步应该做什么。

`/director` 只作为调试/显式入口；正常使用不要求输入命令。

## 核心原则

- **自然语言优先**：作者说人话，不要求记斜杠命令。
- **中文优先**：所有作者可见回复、状态、选项、错误、产物标题和阅读界面必须优先简体中文；英文仅在必要时使用“中文（English）”。内部 ID、路径、命令、机器字段可以保留英文，但不得直接作为作者界面标签。
- **先看状态，再行动**：不得仅凭聊天记忆猜“写到哪了”。
- **推进到下一个作者决策点**：可自动完成无争议的读取、检查、派生更新；遇到创作选择、正式晋升、重大分支时停下来让作者决定。
- **永远提示下一步**：除非作者明确说“不需要建议”，每次任务结束都返回当前状态和推荐下一步。
- **不成为第二套业务逻辑**：小说导演只路由/编排，不复制 00~23 的具体生成规则。
- **不提高派生数据权威**：`author-status.md` 只是导航缓存，不是故事事实。

### 作者可见术语统一

正常回复中优先使用以下中文：

- `Scene` → 场景
- `Scene Plan` → 场景计划
- `Beat Sheet / Beats` → 场景节拍
- `proposed draft` → 待确认草稿
- `canonical prose` → 正式正文
- `candidate` → 候选方案
- `quality gate / Gate` → 质量门禁
- `Chapter Commit` → 章节提交
- `Story Bible` → 故事资料库

除非作者明确询问内部实现，不向作者堆内部英文状态名或 Skill 名称。

## 自然语言入口

典型表达及内部意图：

| 作者表达 | 内部意图 | 默认行为 |
|---|---|---|
| “开一本新书”“我有个新想法” | start-project | `00-project-init` → `01-quick-start`，到需要作者确认时停 |
| “继续”“继续写”“接着写” | resume-writing | 读取当前状态，自动推进到下一作者决策点；若已有明确正式场景计划，可生成一个待确认场景草稿 |
| “下一步呢”“我该干嘛”“现在做什么” | recommend-only | 只诊断状态并给建议，不生成正文、不晋升正式状态 |
| “我卡住了”“不知道怎么写” | unblock | 判断是场景级还是剧情级；场景级走 `21-scene-planning`，重大分支走 `05-next-outline`；只给待确认/候选内容 |
| “推演一下”“给我几个方向” | simulate | 生成候选，不进入正式事实 |
| “这段不行”“改一下这段” | revise-prose | 有明确选区时 `10-polish`；需要续接/插入时 `09-continue-writing` |
| “这版可以”“定稿”“就这样” | approve-current | 仅当存在唯一明确待确认场景时调用 `08-expand confirm`；歧义时列出目标，不猜 |
| “这一章写完了”“收一下这一章” | close-chapter | 完成实际摘要 → 写后一致性检查 → 质量门禁；通过后才章节提交 + 故事资料库更新 |
| “今天先到这” | end-session | 记录本次进度和下次入口；未完成章节不强制提交 |
| “我想改人物/设定” | edit-setting | 路由 `02-setting`，先影响分析，确认后保存 |
| “看看关系”“人物关系怎么样” | inspect-relation | `13-relation-network` |
| “拆一下这本书” | decompose | `15-book-decomposition` |
| “统计一下最近写了多少” | analytics | `19-writing-analysis` |

自然语言不要求精确匹配关键词，应按语义理解。

## 状态读取

每次继续写、只看下一步、收章、结束会话前至少检查：

1. `08-config/project.md`：项目存在性、正文来源、版本方法；
2. `01-brief/`、`02-settings/`：基础创作资产是否已建立；
3. `03-outline/`：总纲/卷纲/当前章纲/场景计划；
4. `06-drafts/`：是否有待确认设定、候选方案、正文草稿、场景计划；
5. 正式正文：按项目正文来源读取；
6. `05-summaries/**` 是否新鲜；
7. `10-analysis/consistency/**`、`quality-gates/**` 是否覆盖当前版本；
8. `11-runtime/commits/**`、`state/current.md`、`bible/**` 的来源和运行状态；
9. `11-runtime/state/author-status.md` 只可作为快速提示，必须用以上来源校验后才能继续使用。

禁止用文件修改时间猜故事顺序；场景顺序仍按 `chapter_id + scene_order`。

## 状态机：优先级

### A. 作者决策优先

若存在：
- 待确认正文；
- 多个候选方案等待选择；
- 设定修改等待保存；
- 质量门禁 P0/P1；
- 重大剧情分支；
则先提示作者处理，不越过决策边界。

### B. 基础资产

若无有效项目 → 初始化项目。
若没有可用创意简报 → 快速开始。
若关键设定未确认 → 设定流程。
若没有可写的计划大纲 → 大纲 / 黄金三章 / 后续大纲。

### C. 场景写作

若当前章有计划大纲但没有场景计划：
- 复杂/关键场景 → `21-scene-planning`；
- 简单过渡场景可由扩写能力生成轻量场景节拍。

若有正式场景计划且无待确认草稿：
- “继续写”可执行写前一致性检查 + 上下文组装 + 扩写，生成**一个**待确认场景；
- “下一步呢”只建议，不自动生成。

若有待确认场景：
- 推荐顺序：查看/修改 → 确认；
- 不自动晋升为正式正文。

若当前场景已正式且本章还有未完成场景：
- 推进下一场景。

### D. 章节收口

仅当章节范围完整：
1. 实际摘要；
2. 写后一致性检查；
3. 质量门禁；
4. 质量门禁通过或带提醒通过 → 章节提交；
5. 故事资料库更新；
6. 推荐下一章规划。

若质量门禁失败：
- 停止章节提交；
- 给出最小修复目标；
- 修复后只重跑受影响检查。

## “继续写”的特殊规则

“继续写”不是“无脑调用续写能力”，而是：**从当前项目状态继续创作**。

- 有未确认草稿 → 先让作者审阅，不另起新正文；
- 有场景计划无草稿 → 可以写当前场景；
- 当前场景尚未写完且作者明确要求接着当前文本 → `09-continue-writing`；
- 当前章没有可写计划 → 先规划，不自由扩张；
- 当前章已经完成 → 先收口，不跳过质量门禁/章节提交直接写下一章。

## “下一步呢”的特殊规则

只做导航，不产生新的创作内容。

必须回答：
- 当前在哪；
- 是否有阻塞；
- 现在最值得做的一件事；
- 最多两个替代动作。

## “定稿”的特殊规则

“这版可以 / 定稿 / 就这样”是高风险自然语言，因为可能触发正式晋升。

只有同时满足以下条件才自动路由到 `08-expand confirm`：
- 当前只有一个待确认正文目标；
- 目标场景 ID 明确；
- 用户表达明确指向当前版本；
- 没有另一个同范围的活跃草稿。

否则不猜目标，只列出需要确认的草稿。

## “今天到这”的特殊规则

结束写作会话时：
- 不为了“流程完整”强迫补写；
- 不把未完成章提交；
- 更新 `author-status.md`；
- 给出一句“下次从哪里继续”；
- 若当前正好整章完成且所有前置都满足，可提示“可以收章”，但除非用户同时表达“收章/定稿”，不自动晋升未确认正文。

## 作者状态缓存

可写：`11-runtime/state/author-status.md`

它是**导航缓存**，不是故事资料库，也不是正式事实。

建议内部字段：

```yaml
authority: derived
runtime_status: fresh | stale
derived_from:
  - <paths/revisions used>
updated_at:
current_chapter:
current_scene:
workflow_stage:
decision_required: true | false
blockers: []
recommended_next:
alternatives: []
```

规则：
- 每次小说导演读取后可刷新；
- 证据版本变化则标记过期；
- 与正式来源 / 有效运行状态冲突时丢弃并重建；
- 不得被 `16-context-assembly` 当故事事实注入。

## 回复契约

面向作者的默认回复保持简短，固定为三块：

```text
当前
第 8 章 / 场景 2，有一版待确认草稿等你确认。

需要你处理
这版还没有进入正式正文。

建议下一步
1. 查看并修改场景 2（推荐）
2. 直接定稿
3. 重新推演这个场景
```

规则：
- “当前”只说对本轮有用的状态；
- “需要你处理”没有事项时可写“没有阻塞”；
- “建议下一步”最多 3 个，第一项必须是推荐动作；
- 不把内部 Skill 名称和英文状态堆给普通作者；只有用户问“后台做了什么”时再说明。

## 自动执行边界

可以自动：
- 状态扫描；
- 新鲜度校验；
- 上下文组装；
- 一致性检查 / 质量门禁；
- 摘要 / 章节提交 / 故事资料库等派生数据更新（前提满足时）；
- 明确计划下生成一个待确认草稿。

必须停下来：
- 候选方案 → 正式计划；
- 待确认正文 → 正式正文（除非用户刚明确“定稿/这版可以”）；
- 修改正式设定；
- 重大剧情分支；
- 删除/覆盖用户正文；
- 质量门禁失败后需要改变故事内容的修复。

## 下游路由

小说导演不复制业务逻辑，只调用对应 Skill。
`00~23` 的读写、权威级别、新鲜度、晋升、质量门禁规则仍以各自 `SKILL.md` 与 Story Repository 契约为准。

## 禁止

- 因为用户说“继续”就跳过未确认草稿。
- 因为流程下一步是章节提交就把计划内容当成已发生事实。
- 为了给建议而制造多余任务。
- 每轮给作者十几个选项。
- 要求作者记住 Skill 编号或命令才能完成正常写作。
- 在作者可见回复里直接输出 `proposed draft / canonical / Scene Plan / Beat Sheet / Gate` 等裸英文状态词。
